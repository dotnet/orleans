# Upgrade Orleans 10.x to 11

This guide covers upgrading an Orleans 10 application or provider to **Orleans 11.0.0-preview.1**. It includes the changes since Orleans 10.4.0 and the compatibility settings needed by clusters which adopted the experimental distributed directory in earlier Orleans 10 releases.

## Starting and target assumptions

- Start from a validated Orleans 10 deployment, preferably 10.4.0. Clusters using the Orleans 10.1 experimental directory must plan [partition identity compatibility](#preserve-experimental-distributed-directory-partition-identities) before taking an intermediate or target runtime upgrade.
- Orleans 11 packages target .NET 8 and .NET 10. Keep the application's target framework unchanged for the first deployment, or qualify retargeting separately.
- Rebuild applications, grain interface assemblies, custom providers, and dependent libraries against the target packages. This release includes source- and binary-breaking changes.
- Record the current directory selection, partition mapping, storage identities, provider schemas, serializer settings, and package graph before changing configuration.

Use a [parallel-cluster deployment](deployment-and-rollback.md) as the default for this cross-major preview upgrade. A mixed-major rolling deployment needs qualification of the exact runtime versions, transports, directories, providers, and application contracts.

## Change summary

| Area | Before | Required upgrade action |
|---|---|---|
| Default grain directory | The eventually consistent `LocalGrainDirectory` | Plan the transition to the stable, strongly consistent distributed directory. Preserve explicit external and named directory selections. |
| Networking | Byte-stream connection options and middleware | Replace removed APIs with message transport connector/listener middleware and rebuild integrations. |
| TLS | Separate `Microsoft.Orleans.Connections.Security` package | Remove that package, update namespaces and callback types, and use TLS from Core/Runtime. |
| Silo hashes | `GetUniformHashCodes(int)` returns `uint[]` | Rebuild for <xref:System.Collections.Immutable.ImmutableArray`1>; preserve directory partition identities. |
| Configuration | Some invalid typed values silently select defaults | Correct invalid values and exercise host construction, options resolution, and startup before rollout. |
| DynamoDB grain storage | Unset `ServiceId` uses an empty prefix | Set the provider's `ServiceId` explicitly; use `string.Empty` to preserve keys written with the old default. |
| Cancellation | Legacy Orleans token types | Migrate to <xref:System.Threading.CancellationToken> and <xref:System.Threading.CancellationTokenSource> through compatible grain-contract changes. |
| Message statistics | Legacy statistics properties and metrics listener | Replace zero-valued statistics with OpenTelemetry message-size histograms. |
| Kubernetes hosting | An open-ended KubernetesClient dependency | Align direct dependencies with `[21.0.8,22.0.0)`. |
| ADO.NET grain storage | Legacy row identities | Keep `Legacy` for existing data; choose `GrainTypeQualified` for new databases or a separately planned data migration. |
| Custom providers and integrations | Row membership reads, older journal assumptions, raw NATS identities | Apply the provider-specific steps below and test rollback against newly written data. |

## Align packages and rebuild

1. Update the solution's `Microsoft.Orleans.*` references centrally to `11.0.0-preview.1`, including clients, servers, SDK, serializers, and installed providers.
1. Select `11.0.0-preview.1.alpha.1` for packages which retain an alpha suffix: journaling and its Azure Storage, Redis, and S3 providers; Durable Jobs and its Azure Storage provider; ADO.NET, Redis, and NATS streaming; and the ADO.NET grain directory.
1. Remove `Microsoft.Orleans.Connections.Security` as described in [Migrate networking and TLS](#migrate-networking-and-tls).
1. Inspect direct and transitive dependencies with `dotnet list package --include-transitive`. Resolve version conflicts and rebuild every deployment artifact, including independently packaged providers.

**Detect problems:** Resolve missing-type, missing-method, obsolete-API, and NuGet dependency diagnostics before rollout. A successful application build alone doesn't rebuild a precompiled third-party transport or provider.

## Plan the default grain-directory transition

Orleans 11 makes the strongly consistent distributed grain directory stable and the default. It coordinates registrations through membership views and numbered partitions. The directory choice is a cluster ownership decision: plan it together with the runtime upgrade.

The move from the local directory to the distributed directory is **one-way**. Once a cluster has moved, reverting it to the local directory is unsupported. Applications can keep the local directory explicitly to defer migration.

Follow the [grain-directory upgrade procedure](../host/grain-directory.md#local-to-distributed-directory-upgrade). Separate the runtime upgrade from the ownership transition using two rollouts:

1. Inventory default-directory grains separately from grains selecting a named or external directory.
1. Upgrade every Orleans 10 silo to Orleans 11 with the local-directory opt-out configured using <xref:Orleans.Hosting.CoreHostingExtensions.UseLocalGrainDirectory*>. Complete this rollout and validate the cluster while all silos still use the local directory.
1. Keep the opt-out to defer migration, or remove it in a second rollout to migrate to the distributed directory. Follow the directory procedure's ordering and health gates.
1. Keep explicit named and external directory selections stable. Qualify silo joins, graceful departures, and abrupt failures under traffic.

**Detect problems:** Check activation uniqueness and directory registration preservation while repeatedly calling the same grain through different silos. Gate rollout on directory/membership errors, duplicate-activation reports, activation failures, and first-call latency. Pause the rollout and investigate registration loss or conflicting ownership before continuing.

### Preserve experimental distributed-directory partition identities

[PR #11425](https://github.com/dotnet/orleans/pull/11425) exposes <xref:Orleans.Configuration.GrainDirectoryOptions.GetPartitionBoundaries> so newer silos can retain the mapping used by an existing cluster.

| Existing distributed-directory cluster | Configuration on newer silos |
|---|---|
| Orleans 10.1: 30 partitions per silo, numbered after sorting uniform hashes | Set <xref:Orleans.Configuration.GrainDirectoryOptions.PartitionsPerSilo> to `30`. Set `GetPartitionBoundaries` to a delegate which obtains the requested uniform hashes and returns them in sorted immutable order using `Sort()`. |
| Orleans 10.2 and later: generated-order mapping | Retain the existing partition count and the default boundary function. |

The count **and** boundary-to-partition mapping must agree on every silo. Preserve them in every deployment using that directory, including retained earlier binaries. Restoring only the count for a 10.1 cluster leaves partition numbers inconsistent.

A custom boundary function returns an initialized immutable array with exactly the requested number of boundaries. Each array index identifies a partition. The function is captured when the directory is created, can run concurrently, and must keep each partition's boundary stable for the silo's membership.

**Detect problems:** An exception or invalid result from the boundary function stops directory membership processing; reads and refreshes report <xref:Orleans.Runtime.OrleansConfigurationException>. Correct the configuration and restart affected silos. Test registration preservation and single activation during ownership transfer as well as startup.

Changing an established cluster's count or mapping requires a coordinated full-cluster restart or a blue-green cutover with controlled grain-state ownership. See [Distributed-directory upgrade compatibility](../deployment/upgrades.md#distributed-directory-upgrade-compatibility).

### Rebuild uniform-hash callers

<xref:Orleans.Runtime.SiloAddress.GetUniformHashCodes*> now returns `ImmutableArray<uint>` instead of `uint[]` for **every caller**, including custom directories and code outside the directory subsystem.

Recompile callers against the new signature. Use the immutable result directly for read-only access, `ToArray()` for an independently mutable buffer, or `Sort()` for a sorted immutable result. The cached hash storage remains immutable.

**Detect problems:** Look for array assignments and in-place sorting in source, and rebuild precompiled libraries which call this method. Previously compiled callers can fail with <xref:System.MissingMethodException>.

## Migrate networking and TLS

[PR #10074](https://github.com/dotnet/orleans/pull/10074) replaces the byte-stream connection infrastructure with message-oriented transports. Applications using the built-in transport update their packages; custom connection integrations must adopt the new contracts.

### Replace connection options and middleware

| Removed API or customization | Replacement |
|---|---|
| `ClientConnectionOptions.ConfigureConnection` and outbound silo connection callbacks | Register <xref:Orleans.Connections.Transport.IMessageTransportConnectorMiddleware> as a singleton in dependency injection. Return a connector decorator. |
| `SiloConnectionOptions` inbound silo/gateway callbacks | Register <xref:Orleans.Connections.Transport.IMessageTransportListenerMiddleware> as a singleton. Use listener names `silo` and `gateway` to distinguish roles. |
| `IConnectionMiddleware` and `ConnectionMiddlewareExtensions.UseMiddleware` | Move behavior into connector/listener decorators and, where needed, decorate the resulting <xref:Orleans.Connections.Transport.MessageTransport>. |
| `SocketConnectionOptions`, `SocketConnectionException`, and `ConnectionFrameHelper` | Port custom socket configuration, exception handling, and framing to the message transport contracts. |
| Byte-stream TLS middleware (`TlsConnectionBuilderExtensions`) | Use the built-in client/silo `UseTls` hosting extensions. |

Middleware executes in dependency-injection registration order. Preserve connector/listener features, validity, listener names, cancellation, and disposal when decorating. Custom transports implement the read/write request completion and buffer-lifetime contracts; treat this as a transport port rather than a mechanical type rename.

See [Message transport middleware](../host/connection-middleware.md) and the API references for <xref:Orleans.Connections.Transport.MessageTransportConnector>, <xref:Orleans.Connections.Transport.MessageTransportListener>, <xref:Orleans.Connections.Transport.ReadRequest>, and <xref:Orleans.Connections.Transport.WriteRequest>.

**Detect problems:** Search source and configuration for the removed names, including shared hosting libraries. Test silo-to-silo and client-to-gateway connections, reconnects, handshake cancellation, shutdown, partial reads, and failed sends. Run the same tests across old/new endpoints before qualifying a mixed-version deployment.

### Consolidate TLS references

1. Remove the `Microsoft.Orleans.Connections.Security` package reference. TLS now comes through the client/server dependency graph in Core and Runtime.
1. Replace `Orleans.Connections.Security` imports with `Orleans.Connections.Transport.Security` for TLS options, certificate modes, features, delegates, and <xref:Orleans.Connections.Transport.Security.CertificateLoader>.
1. Keep extension-call syntax such as `builder.UseTls(...)`. Replace explicit static calls to `OrleansConnectionSecurityHostingExtensions` with <xref:Orleans.Hosting.ClientTlsHostingExtensions> or <xref:Orleans.Hosting.SiloTlsHostingExtensions>.
1. Update certificate selectors and authentication callbacks which explicitly accept `ConnectionContext` to accept `MessageTransport`; access connection features through its feature collection.
1. Rebuild dependent libraries as well as the application, and retest certificate selection, chain/name validation, and rotation.

The `Orleans1` ALPN identifier and certificate-mode defaults are preserved. Inbound silo connections still default to requiring a peer certificate; retain the explicit certificate modes used by your authentication model. See [Secure Orleans connections with TLS](../host/transport-layer-security.md#migrate-tls-configuration).

**Detect problems:** Compile errors identify namespace and callback-signature changes. Assembly/type-load failures identify binaries still referencing the retired security assembly. Monitor TLS authentication and reconnect failures on both silo and gateway connections, using the production trust and certificate policy.

## Correct invalid configuration before deployment

[PR #11521](https://github.com/dotnet/orleans/pull/11521) and [PR #11522](https://github.com/dotnet/orleans/pull/11522) make invalid typed configuration values fail with <xref:System.InvalidOperationException> instead of silently retaining defaults or dropping entries.

Affected configuration-based provider paths include:

- Cosmos clustering.
- DynamoDB grain storage, clustering, and reminders.
- Redis streaming and journaling.
- Azure Queue streaming and Azure Table journaling settings.
- Memory grain storage.
- `Orleans:Endpoints`, `Orleans:Clustering:Gateways`, and `Orleans:EnableDistributedTracing` on clients and silos.

For example, replace a mistyped `SiloPort` value such as `"1111l"` with `11111`, or omit the key when the default is intended. Fix every invalid static gateway endpoint; each configured entry now has to parse.

Provider settings use <xref:Microsoft.Extensions.Configuration.ConfigurationBinder.GetValue*>. Missing keys retain defaults. Whitespace-only typed values fail; empty strings retain defaults with Binder 10.x but fail with Binder 8.x used by the .NET 8 assets. The Core/Runtime endpoint and tracing parser retains defaults for absent or empty strings and rejects whitespace-only or malformed values. **Omit unused typed keys** for consistent behavior across targets. The explicit empty DynamoDB `ServiceId` described below is a string identity, not an unused typed setting.

**Detect problems:** Build and start real client/silo hosts with the deployed JSON, environment variables, and secret-provider configuration. Resolve configured providers and options: failures can occur during host construction or first options resolution. The exception identifies the configuration path and target type. Include negative configuration cases in deployment smoke tests so a typo fails before a production rollout.

## Set the DynamoDB grain-storage service identity

[PR #11551](https://github.com/dotnet/orleans/pull/11551) requires <xref:Orleans.Configuration.DynamoDBStorageOptions.ServiceId> to be set explicitly for **each grain storage provider**.

| Existing configuration | Upgrade configuration |
|---|---|
| `ServiceId` omitted, using the old empty-string default | Set `ServiceId` to `string.Empty` in code or `""` in configuration. |
| Explicit nonempty `ServiceId` | Keep exactly the same value. |
| New state namespace | Choose a stable identifier, for example the application's <xref:Orleans.Configuration.ClusterOptions.ServiceId>. |

The provider keys state as `{ServiceId}_{grainId}`. Setting only the cluster's service identity doesn't configure the storage provider's identity. For an existing configuration-based provider, retain its other settings and add the explicit empty value when preserving the old default:

```json
{
  "Orleans": {
    "GrainStorage": {
      "Default": {
        "ProviderType": "DynamoDB",
        "ServiceId": ""
      }
    }
  }
}
```

Keep the table, prefix, and serializer unchanged during rollout and rollback. A new prefix is a separate namespace and needs an application-owned data migration to expose existing state there.

**Detect problems:** An unset value now produces an `OrleansConfigurationException` at startup. A changed prefix can instead make grains appear to have fresh state; compare representative pre-upgrade item keys and read known existing state before allowing writes. See [DynamoDB service identity and upgrades](../grains/grain-persistence/dynamodb-storage.md#service-identity-and-upgrades).

## Migrate obsolete message statistics

[PR #11560](https://github.com/dotnet/orleans/pull/11560) makes <xref:Orleans.Runtime.SiloRuntimeStatistics.ReceivedMessages>, <xref:Orleans.Runtime.SiloRuntimeStatistics.SentMessages>, and <xref:Orleans.Runtime.SiloRuntimeMetricsListener> obsolete. Their message-byte values always reported zero because the listener was never started.

Use the OpenTelemetry `orleans-messaging-received-messages-size` and `orleans-messaging-sent-messages-size` histograms instead. Update dashboards, health checks, and autoscaling code which consume the old properties or listener. Histogram sums provide the replacement byte totals since collection began; histogram counts measure message volume. Preserve emitting-silo identity, handle the exporter's cumulative or delta temporality, and scope meter collection when several Orleans runtimes share a process.

**Detect problems:** Review obsolete warnings and search consumers of silo statistics. Send and receive known traffic and verify the exported histogram observations and dashboard aggregations. See [Orleans metrics](../host/monitoring/metrics-catalog.md).

## Align KubernetesClient dependencies

[PR #11503](https://github.com/dotnet/orleans/pull/11503) compiles `Microsoft.Orleans.Hosting.Kubernetes` against KubernetesClient `21.0.8` and constrains its supported dependency range to **`[21.0.8,22.0.0)`**.

Update direct KubernetesClient references, central package entries, and lock files to a version in that range. Rebuild code calling the Kubernetes API, whose generated pod-operation signatures can change between major versions.

**Detect problems:** Inspect the resolved package graph for an out-of-range selection, then start a silo with the actual Kubernetes hosting configuration. Earlier Orleans hosting binaries combined with KubernetesClient 21.x can fail in `KubernetesClusterAgent.OnStart` with `MissingMethodException`; deploy the rebuilt hosting package and its matching dependency together.

## Choose ADO.NET grain-storage keys deliberately

[PR #11516](https://github.com/dotnet/orleans/pull/11516) adds <xref:Orleans.Configuration.AdoNetGrainStorageOptions.KeyFormat>. The default remains <xref:Orleans.Configuration.AdoNetGrainStorageKeyFormat.Legacy>.

| Storage situation | Action |
|---|---|
| Existing database or Orleans 3-compatible hashing | Keep `Legacy` through upgrade and rollback. |
| New database | Select <xref:Orleans.Configuration.AdoNetGrainStorageKeyFormat.GrainTypeQualified>. |
| Existing data moving to qualified keys | Plan a quiesced, application-owned data migration or cutover separately from the runtime upgrade. |

`GrainTypeQualified` preserves the exact bytes of grain type, state name, and key using hexadecimal key columns. It separates grain types sharing a state name and key, string keys such as `"20235"` and `"020235"`, and identities which a database collation otherwise equates. The existing SQL scripts support it.

Changing the format changes row identities. Existing legacy rows contain insufficient information to recover their grain type automatically. Both rollout versions must address the same identities; reverting the option after qualified writes selects the legacy rows again. Include data conversion or restoration in any rollback across formats.

Qualified grain keys, and grain type plus state name, are each limited to about 255 bytes by the key columns. Longer identities throw <xref:System.ArgumentException>. Qualified keys and `UseOrleans3CompatibleHasher()` are incompatible.

**Detect problems:** With `Legacy`, test two grain types sharing the same state name and key, plus distinct string keys which parse to the same number. Collisions can return another grain's state or cause deserialization failures. Before enabling qualified keys, test representative maximum-length identities and verify old-state reads. See [ADO.NET grain persistence](../grains/grain-persistence/relational-storage.md) and the [key-format reference](https://github.com/dotnet/orleans/blob/main/src/AdoNet/Orleans.Persistence.AdoNet/README.md#storage-key-format).

## Update provider integrations

### Use coherent membership snapshots

[PR #11389](https://github.com/dotnet/orleans/pull/11389) makes <xref:Orleans.IMembershipTable.ReadRow*> and <xref:Orleans.IMembershipTable.ReadRowAsync*> obsolete. Built-in providers honor pre-cancellation and otherwise report <xref:System.NotSupportedException> for these operations.

Replace custom diagnostic and provider-test row reads with <xref:Orleans.IMembershipTable.ReadAllAsync*>, then select the row using <xref:Orleans.MembershipTableData.TryGet*>. Obtain the row, its ETag, and the table version from that **same snapshot**. Keep legacy interface/RPC compatibility when maintaining a provider used by older runtimes.

**Detect problems:** Search custom tools and conformance tests for the old calls. Exercise present and absent rows, cancellation, and concurrent membership changes; check that row ETags and table versions come from one read.

### Coordinate NATS publisher and consumer upgrades

[PR #11429](https://github.com/dotnet/orleans/pull/11429) preserves dotted, reserved, and binary stream identities by encoding subject components and, where needed, writing a byte-preserving JSON identity.

Pause producers, drain deliverable messages, upgrade every provider-using silo and client, then resume publishing. Safe existing subjects keep their partitions; escaped identities can move partitions. The new provider reads legacy messages, while older consumers can't read the new byte-component representation.

**Detect problems:** Test dotted/wildcard names, literal `~` prefixes, namespace `null`, empty namespaces, slash-containing namespaces, and binary identities. Compare acknowledged messages with actual delivery. Previously stranded messages on unpartitioned subjects need replay through the upgraded provider. For rollback, first drain or transform messages using the new representation and coordinate publishers/consumers again. See [NATS JetStream streaming](../streaming/stream-providers.md#nats-jetstream-streaming-alpha).

### Treat ADO.NET stream tokens as local positions

[PR #11527](https://github.com/dotnet/orleans/pull/11527) changes an ADO.NET stream token's `SequenceNumber` from the database `MessageId` to a local queue-cache position. Remove application or diagnostic assumptions equating the two. The token remains <xref:Orleans.Providers.Streams.Common.EventSequenceTokenV2>, and database schemas and SQL scripts remain compatible.

**Detect problems:** Test out-of-order dequeues and redelivery after visibility timeout, silo retirement, and rebalance. Assert consumer delivery rather than comparing token values with database row IDs.

### Preserve journal namespaces and enforce handle preconditions

For applications using the experimental journaling packages:

- [PR #11409](https://github.com/dotnet/orleans/pull/11409) adds <xref:Orleans.Journaling.JournalStorageProviderAttribute>. Keep the existing default or named physical namespace stable across silos and rollback. Changing a grain type's selection for existing journals needs a data migration or cutover. Missing registrations fail with contextual configuration errors.
- [PR #11537](https://github.com/dotnet/orleans/pull/11537) enforces <xref:Orleans.Journaling.IJournalStorage> contracts. Custom providers return fresh storage handles; callers serialize operations per handle and establish a write precondition with a successful read or creation before writing. Subsequent reads validate that content version. Recover conflicts using a fresh handle, enforce atomic ordered content, and submit nonempty append segments.
- [PR #11471](https://github.com/dotnet/orleans/pull/11471) changes volatile snapshot policy to 100 successful appends or 1 MiB of appended encoded bytes. Set <xref:Orleans.Journaling.VolatileJournalStorageOptions> explicitly if tests or workloads need another snapshot cadence.
- [PR #11552](https://github.com/dotnet/orleans/pull/11552) makes successful state deletion discard pending entries along with in-memory state. Perform intended post-deletion mutations after deletion completes.

**Detect problems:** Test recovery, stale writers, simultaneous creation, lost responses, provider limits, deletion with pending writes, and reconstruction on a fresh activation. A write before recovery reports `InvalidOperationException`; a stale handle reports <xref:Orleans.Storage.InconsistentStateException>. An indeterminate write can have committed despite its final exception: recover the durable outcome before retrying application work. Compare snapshot latency and memory under load. See [journal configuration](../grains/journaling/configuration.md) and [runtime behavior and consistency](../grains/journaling/runtime-behavior.md).

## Requalify runtime and serialization behavior

These fixes can expose assumptions in application code even where the public signature is unchanged:

| Change | Action and detection |
|---|---|
| Lifecycle timeouts ([#11514](https://github.com/dotnet/orleans/pull/11514)) | Make `OnStart`, `OnActivateAsync`, `OnDeactivateAsync`, and `OnStop` promptly observe their cancellation tokens. Orleans awaits callbacks to completion before releasing activation registration and scoped services; a timed-out activation still fails after its callback returns. Handle cancellation as <xref:System.OperationCanceledException> rather than requiring its `TaskCanceledException` subtype. Test canceled callbacks and shutdown budgets. A callback that remains blocked keeps its lifecycle transition pending. See [activation collection](../host/configuration-guide/activation-collection.md). |
| Read-only admission ([#10809](https://github.com/dotnet/orleans/pull/10809)) | Writable requests now wait for every incompatible active read-only request; heterogeneous `MayInterleave` cohorts are checked pairwise. Remove dependencies on the earlier overlap and test read/write ordering and completion order. See [request scheduling](../grains/request-scheduling.md). |
| Grain timers ([#11464](https://github.com/dotnet/orleans/pull/11464)) | Queued/running ticks coalesce. Changes made while a tick is queued or running select its following schedule; the latest due time and period win. Test immediate ticks, repeated `Change` calls, cancellation, and disposal rather than assuming a queued callback disappears after a schedule change. |
| Observer filters ([#11507](https://github.com/dotnet/orleans/pull/11507)) | Observer-level incoming filters now run even with no system-wide incoming filters. Exercise authorization, logging, and result transformations on observers to detect newly effective filter behavior. |
| Redis clustering/directory routing ([#11484](https://github.com/dotnet/orleans/pull/11484)) | These providers require primary routing for membership and directory reads/scripts. Verify primary reachability and failover, and alert on command failures; replica connectivity alone doesn't establish provider readiness. |
| Serialization type grants ([#11456](https://github.com/dotnet/orleans/pull/11456)) | Authorize intended generic definitions independently of their arguments using manifest/name/assembly grants or <xref:Orleans.Serialization.ITypeFilter>. Use valid assembly-qualified names, including supported type forwarding. Test persisted polymorphic state and queued payloads; an unauthorized type produces `InvalidOperationException`. Preserve narrow grants and explicit argument denials. See [serialization type-name authorization](../host/configuration-guide/serialization-configuration.md#authorize-type-name-resolution). |
| Custom Arc-buffer consumers ([#11474](https://github.com/dotnet/orleans/pull/11474)) | <xref:Orleans.Serialization.Buffers.ArcBuffer.First> is nullable for owner-free empty buffers. Observe constructor bounds and borrowed-reader lifetimes, and test empty, sliced, and disposed buffers. Invalid bounds or disposed access now fail explicitly. |
| Graceful retirement ([#11460](https://github.com/dotnet/orleans/pull/11460)) | Size shutdown budgets for activation migration and caller retargeting. New destinations can accept queued requests; older destinations use request-free migration and ordinary forwarding. Test completion, timeout, cancellation, and retries during departure. Retargeting is best effort and preserves the original caller deadline. |

ADO.NET, Azure Blob, Azure Table, Cosmos DB, DynamoDB, and Firestore grain storage also forward cancellation to their SDK/driver operations. Test cancellation with real provider I/O and recover uncertain write outcomes before retrying. Keep side effects and retries idempotent.

For custom buffer integrations, <xref:Orleans.Serialization.Buffers.ArcBufferWriter.MinimumPageSize> increases from 1 KiB to 16 KiB with the transport change. Rebuild code which embeds that constant and revisit fixed-capacity assumptions. The built-in codec and copier added in [PR #11463](https://github.com/dotnet/orleans/pull/11463) return independently owned buffers: dispose each acquired handle once and acquire an independent pin before handing a borrowed struct copy to a longer-lived owner.

## Deploy and retain rollback

Follow [Upgrade deployment and rollback](deployment-and-rollback.md), with these release-specific gates:

1. Retain the Orleans 10 image, dependency lock files, configuration, and a recoverable provider-data checkpoint.
1. Rehearse the one-way directory transition independently from storage-key, journal-namespace, serializer, and grain-contract migrations. Retain a recovery build compatible with the directory the cluster will use.
1. Test known old-state reads, new writes, clears, and rollback reads for each provider before admitting production writes.
1. For a qualified rolling deployment, keep directory mappings, TLS policy, storage identities, and shared contracts compatible throughout coexistence. Coordinate NATS separately.
1. For blue-green deployment, isolate membership using distinct cluster identities and quiesce the old cluster before handing over shared mutable state.
1. Gate each traffic increase on activation uniqueness, directory registration, membership health, TLS connections, request latency/failure rate, storage errors, and stream delivery.
1. Drain traffic before reverting application/runtime binaries. Restore data when the retained build can't read new formats or namespaces; deploy code and configuration compatible with the cluster's current directory and storage identities.

- [ ] Align KubernetesClient and deliberately retain or migrate ADO.NET key identities.
