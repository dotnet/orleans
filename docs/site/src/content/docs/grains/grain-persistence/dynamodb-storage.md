## Capacity and lifecycle

<xref:Orleans.Configuration.DynamoDBStorageOptions.UseProvisionedThroughput> selects provisioned-capacity behavior. When enabled, configure <xref:Orleans.Configuration.DynamoDBStorageOptions.ReadCapacityUnits> and <xref:Orleans.Configuration.DynamoDBStorageOptions.WriteCapacityUnits>. <xref:Orleans.Configuration.DynamoDBStorageOptions.CreateIfNotExists> and <xref:Orleans.Configuration.DynamoDBStorageOptions.UpdateIfExists> allow provider-managed table changes, but infrastructure-managed provisioning is usually preferable in production.

<xref:Orleans.Configuration.DynamoDBStorageOptions.DeleteStateOnClear> controls whether clearing state deletes the item or resets it. <xref:Orleans.Configuration.DynamoDBStorageOptions.TimeToLive> advances the item's expiration on every write; enable it only when disappearing state is valid application behavior.

<xref:Orleans.Configuration.DynamoDBStorageOptions.ServiceId> must remain stable across deployments that share the same logical application state. The provider uses optimistic concurrency and rejects stale writes.

When <xref:Orleans.Configuration.DynamoDBStorageOptions.ServiceId> is empty, the keys are built from <xref:Orleans.Configuration.ClusterOptions.ServiceId>, as in the other grain storage providers. Earlier versions left it empty, so the keys start with an underscore, and the provider fails to start until <xref:Orleans.Configuration.DynamoDBStorageOptions.UseClusterServiceId> is set when its table records that empty <xref:Orleans.Configuration.DynamoDBStorageOptions.ServiceId>, or holds state written with it: `false` keeps the empty <xref:Orleans.Configuration.DynamoDBStorageOptions.ServiceId>, with a warning, and `true` uses <xref:Orleans.Configuration.ClusterOptions.ServiceId>. A table that records the empty <xref:Orleans.Configuration.DynamoDBStorageOptions.ServiceId>, chosen by a silo of the version that introduced <xref:Orleans.Configuration.DynamoDBStorageOptions.UseClusterServiceId>, stops the provider even when it holds no such state yet, since the silos that chose it may still be writing those keys. A table without a record, from an older version, is checked for state: when upgrading from such a version, stop the silos that run it first, or set <xref:Orleans.Configuration.DynamoDBStorageOptions.UseClusterServiceId> explicitly, since they keep writing keys with an empty <xref:Orleans.Configuration.DynamoDBStorageOptions.ServiceId> that this version would not find. The check reads every key starting with an underscore as such state, which state written with a <xref:Orleans.Configuration.DynamoDBStorageOptions.ServiceId> that starts with an underscore also is, since the two cannot be told apart: set <xref:Orleans.Configuration.DynamoDBStorageOptions.UseClusterServiceId> explicitly in that case as well. State written before then stays under its old key unless <xref:Orleans.Configuration.DynamoDBStorageOptions.MigrateLegacyKeys> is also set: a grain with no state under the new key then reads it from the old one, and its next write moves it, in one transaction; a grain that has state under the new key keeps it, and its next write or clear deletes the old item in the same transaction. Set <xref:Orleans.Configuration.DynamoDBStorageOptions.MigrateLegacyKeys> together with <xref:Orleans.Configuration.DynamoDBStorageOptions.UseClusterServiceId>: once the keys have been built from <xref:Orleans.Configuration.ClusterOptions.ServiceId> without a migration, the provider refuses to start one, since a grain whose state there has since been deleted or has expired would read back its older state. Enable the migration once every silo runs a version that supports it, with the same options on every silo: a silo still writing the old keys, from an older version or with <xref:Orleans.Configuration.DynamoDBStorageOptions.UseClusterServiceId> set to `false`, is not protected from a migrating silo moving or deleting state it recreates, since an item recreated after <xref:Orleans.Configuration.DynamoDBStorageOptions.DeleteStateOnClear> starts again at ETag 0. While the migration is on, every write or clear is a transaction over two items, which uses more write capacity; set <xref:Orleans.Configuration.DynamoDBStorageOptions.MigrateLegacyKeys> to `false` when every grain has been written, to spare that and the second read for grains that have no state. The provider records its choice in the table, once for the whole table, so every provider that uses the table with an empty <xref:Orleans.Configuration.DynamoDBStorageOptions.ServiceId> must have the same options. It keeps that choice while these options are left unset, and refuses to start with <xref:Orleans.Configuration.DynamoDBStorageOptions.UseClusterServiceId> set to `false` once the table records <xref:Orleans.Configuration.ClusterOptions.ServiceId>, since the state written since would not be found.

## Serialization

Set <xref:Orleans.Configuration.DynamoDBStorageOptions.GrainStorageSerializer> to customize the stored representation. Changing serializers doesn't rewrite existing items, so the replacement must read the previous representation or be accompanied by a migration.
